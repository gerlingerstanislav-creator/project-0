# PROJECT.md

## Назначение

Этот файл содержит общие правила ведения проекта, которые не относятся только к Laravel.

### Источники истины

- `README.md` — пользовательское описание проекта: назначение, доступные разделы и заметные возможности.
- `LARAVEL_RULES.md` — технические правила реализации Laravel.
- `PROJECT.md` — общие правила проекта: коммиты, документация, интерфейс, структура и безопасность.

Если правило изменилось, сначала обнови соответствующий файл, чтобы следующему разработчику или ИИ не приходилось восстанавливать договорённость из истории чата.

## README.md перед каждым коммитом

Перед **каждым коммитом**:

1. Открой `README.md`.
2. Сверь задачу с текущим описанием проекта.
3. Проверь, появилось ли новое пользовательское поведение, раздел или заметная возможность.
4. Если да — обнови `README.md` в том же коммите.

README должен быть коротким, понятным человеку без знания исходного кода и достаточно конкретным для ИИ, чтобы понять текущее состояние пользовательской части проекта.

В README не записываются пароли, токены, приватные адреса, внутренние секреты и другая чувствительная служебная информация.

## Коммиты

- Одна законченная логическая задача — один коммит.
- Если задача меняет несколько файлов, все изменения входят в один коммит.
- Не дроби одну задачу на несколько коммитов только из-за количества изменённых файлов.
- Сообщение коммита должно кратко описывать результат, а не процесс работы.

## Интерфейс

- Основной язык пользовательского интерфейса — русский.
- Любой новый или изменённый интерфейс сразу адаптируется под мобильные устройства.
- Сохраняй единый визуальный стиль между разделами.
- Навигация и основные действия должны быть понятны без подсказок разработчика.
- Не добавляй декоративные элементы, которые мешают читаемости или взаимодействию.

## Структура

- Повторяющиеся элементы интерфейса выносятся в компоненты.
- Логика, представление, стили и JavaScript находятся в соответствующих слоях.
- Laravel-специфические решения сверяй с `LARAVEL_RULES.md`.
- Не создавай параллельные способы решения одной и той же задачи без необходимости.

## Документация для человека и ИИ

Документация должна быть одновременно читаемой человеком и однозначной для ИИ, который продолжит проект.

Поэтому:

- используй реальные пути файлов и каталогов;
- фиксируй обязательные правила в повелительной форме;
- явно отделяй правила от описания текущего состояния;
- не полагайся на неявные договорённости из истории чата;
- при изменении правил сначала обновляй документацию;
- не добавляй в документацию то, что не соответствует фактическому состоянию репозитория.

## Безопасность

- Не записывай секреты и пароли в исходники.
- Не переносите GitHub Secrets в README, PROJECT.md, LARAVEL_RULES.md и другие отслеживаемые файлы.
- Недоверенные данные GitHub Actions передавай в shell через переменные окружения, а не встраивай напрямую в исполняемый код.

## Definition of Done

Задача считается законченной, когда:

- функциональность реализована;
- мобильная версия учтена;
- код находится в правильном слое;
- README проверен и при необходимости обновлён;
- правила документации соблюдены;
- задача оформлена одним логическим коммитом;
- CI и связанные проверки не сломаны.
