# PROJECT.md

## Назначение

Этот файл содержит общие правила ведения проекта, которые не относятся только к Laravel.

### Источники истины

- `README.md` — пользовательское описание проекта: назначение, доступные разделы и заметные возможности.
- `LARAVEL_RULES.md` — технические правила реализации Laravel.
- `PROJECT.md` — общие правила проекта: коммиты, документация, интерфейс, структура и безопасность.

Если правило изменилось, сначала обнови соответствующий файл, чтобы следующему разработчику или ИИ не приходилось восстанавливать договорённость из истории чата.


## Проверка кода перед сборкой

После написания или изменения кода, но до запуска сборки, обязательно провести собственное ревью изменённого кода на предмет синтаксических ошибок.
- Проверить синтаксис всех изменённых файлов соответствующими инструментами проекта.
- Отдельно проверить скобки, кавычки, точки с запятой, закрытие блоков/функций и другие конструкции, способные привести к ошибке сборки.
- Не запускать сборку до завершения этой проверки.

## Уточнение неточных задач

Если задача пользователя сформулирована неточно, неоднозначно или допускает несколько существенно разных трактовок, не выбирай трактовку самостоятельно. Сначала задай достаточное количество конкретных уточняющих вопросов, чтобы задача стала однозначной для реализации. Вопросы должны покрывать только те неопределённости, которые действительно влияют на результат. Не начинай изменение кода, пока критичные неоднозначности не устранены.


В начале каждой новой задачи по репозиторию обязательно:

1. Просмотри структуру репозитория и найди все файлы, содержащие правила или инструкции для разработчиков/ИИ.
2. Прочитай все найденные применимые файлы правил **до изменения любого файла**.
3. В первую очередь проверь `PROJECT.md` и `LARAVEL_RULES.md`, если они существуют.
4. Если в репозитории появились новые файлы с правилами, учитывай их в текущей задаче.
5. Не полагайся только на список известных файлов: набор правил нужно проверять по фактической структуре репозитория в начале новой задачи.

Это обязательный первый шаг каждой новой задачи по репозиторию.

## README.md перед каждым коммитом

Перед **каждым коммитом**:

1. Открой `README.md`.
2. Сверь задачу с текущим описанием проекта.
3. Проверь, появилось ли новое пользовательское поведение, раздел или заметная возможность.
4. Если да — обнови `README.md` в том же коммите.

README должен быть коротким, понятным человеку без знания исходного кода и достаточно конкретным для ИИ, чтобы понять текущее состояние пользовательской части проекта.

В README не записываются пароли, токены, приватные адреса, внутренние секреты и другая чувствительная служебная информация.

## Коммиты

### 1. Одна логическая задача — один коммит

- Одна законченная логическая задача оформляется одним коммитом.
- Если одна задача меняет несколько файлов одного направления, все эти изменения входят в один коммит.
- Не дроби одну задачу на несколько коммитов только из-за количества изменённых файлов.
- Сообщение коммита должно кратко описывать результат, а не процесс работы.

### 2. Разные направления работы — разные коммиты

Перед созданием коммита определи, к какому направлению относится каждое изменение.

К отдельным направлениям относятся, например:

- CI/CD и GitHub Actions;
- пользовательский интерфейс и frontend;
- backend и бизнес-логика;
- база данных и миграции;
- документация;
- инфраструктура и deployment;
- тесты.

Если потенциальный коммит затрагивает **несколько разных блоков, разделов или направлений деятельности**, раздели изменения на несколько коммитов.

Пример:

- изменение workflow GitHub Actions → отдельный коммит;
- изменение Blade/CSS/JS интерфейса → отдельный коммит.

Не объединяй CI/CD с изменением интерфейса только потому, что эти изменения появились в рамках одной большой задачи.

Исключение: если одно направление технически невозможно отделить от другого без потери целостности изменения, допустимо объединить их, но сообщение коммита должно явно описывать связанную задачу.

Цель — чтобы каждый коммит представлял **одну понятную и изолированную область изменения**. Такой подход упрощает просмотр истории, ревью и откат отдельных изменений. GitHub также рекомендует небольшие, осмысленные и изолированные коммиты. citeturn751152search6turn751152search7

## Интерфейс

- Основной язык пользовательского интерфейса — русский.
- Любой новый или изменённый интерфейс сразу адаптируется под мобильные устройства.
- Сохраняй единый визуальный стиль между разделами.
- Навигация и основные действия должны быть понятны без подсказок разработчика.
- Не добавляй декоративные элементы, которые мешают читаемости или взаимодействию.

## Структура

- Повторяющиеся элементы интерфейса выносятся в компоненты.
- Логика, представление, стили и JavaScript находятся в соответствующих слоях.
- Laravel-специфические решения сверяй с `LARAVEL_RULES.md`.
- Не создавай параллельные способы решения одной и той же задачи без необходимости.

## Документация для человека и ИИ

Документация должна быть одновременно читаемой человеком и однозначной для ИИ, который продолжит проект.

Поэтому:

- используй реальные пути файлов и каталогов;
- фиксируй обязательные правила в повелительной форме;
- явно отделяй правила от описания текущего состояния;
- не полагайся на неявные договорённости из истории чата;
- при изменении правил сначала обновляй документацию;
- не добавляй в документацию то, что не соответствует фактическому состоянию репозитория.

## Безопасность

- Не записывай секреты и пароли в исходники.
- Не переносите GitHub Secrets в README, PROJECT.md, LARAVEL_RULES.md и другие отслеживаемые файлы.
- Недоверенные данные GitHub Actions передавай в shell через переменные окружения, а не встраивай напрямую в исполняемый код.

## Definition of Done

Задача считается законченной, когда:

- функциональность реализована;
- мобильная версия учтена;
- код находится в правильном слое;
- README проверен и при необходимости обновлён;
- изменения одного направления не смешаны с несвязанными направлениями в одном коммите;
- правила документации соблюдены;
- каждый коммит содержит одну логическую и понятную область изменения;
- CI и связанные проверки не сломаны.

## CI/CD и ошибки деплоя

Если пользователь сообщает, что в деплое есть ошибка:

1. Найди последний неуспешный workflow/deployment для актуального push в `main`.
2. Открой логи неуспешного job и определи конкретную причину ошибки, а не предполагай её.
3. Найди связанный с ошибкой код, конфигурацию или тест.
4. Исправь проблему в репозитории.
5. Запушь исправление в `main`.
6. Проверь новый workflow после push и, если он снова падает, продолжи разбор по его логам.
7. В итоговом отчёте укажи причину ошибки, внесённое исправление, commit и текущий статус CI/deploy.
8. Отдельно укажи статус документации.

При диагностике используй логи GitHub Actions.

## Отчёт о документации после push

После каждого push изменений в ветку в итоговом отчёте отдельной строкой указывай статус документации.

Если документация была обновлена, укажи это явно. Если для изменения документация не требовала обновления, также укажи это явно.

Это правило относится к каждому push, который выполняется в рамках работы над проектом.
