# AGENTS.md

## Назначение

Этот файл содержит единые правила работы разработчика и AI-агента с проектом. Считай его главным источником технических правил репозитория.

## Источники истины и порядок приоритетов

- `README.md` — пользовательское описание проекта, доступных разделов и заметных возможностей.
- `AGENTS.md` — обязательные правила разработки, архитектуры, Git, CI/CD, документации и безопасности.
- Актуальная официальная документация Laravel — внешний источник истины для Laravel-специфических решений.
- Существующая архитектура и код проекта — источник текущего фактического состояния.

Если правило проекта изменилось, сначала обнови этот файл, чтобы следующему разработчику или AI-агенту не приходилось восстанавливать договорённость из истории чата.

## Официальная документация Laravel

- Для любой Laravel-специфической задачи сверяй решение с актуальной официальной документацией Laravel.
- Учитывай фактическую версию Laravel, указанную в проекте; не применяй инструкции для другой major-версии без проверки совместимости.
- В первую очередь сверяй соответствующие разделы документации по структуре приложения, Blade, маршрутам, контроллерам, Vite, конфигурации, базе данных, тестированию и deployment.
- Если официальная документация и старое локальное правило расходятся, сначала определи, относится ли различие к версии проекта; затем сохраняй локальное правило только там, где оно является осознанным проектным ограничением и не противоречит Laravel.
- Не добавляй собственный Laravel-паттерн только потому, что он привычен: сначала проверь официальный рекомендуемый способ.

## Перед началом каждой новой задачи

1. Просмотри фактическую структуру репозитория.
2. Найди все файлы, содержащие правила или инструкции для разработчиков/AI.
3. Прочитай все применимые правила до изменения любого файла.
4. В первую очередь проверь `AGENTS.md`, если он существует.
5. Если появились новые файлы с правилами, учитывай их в текущей задаче.
6. Не полагайся только на список известных файлов: набор правил проверяй по фактической структуре репозитория.
7. Для Laravel-задач после чтения локальных правил сверяйся с актуальной официальной документацией Laravel.
8. Перед началом реализации проверь `README.md`, чтобы понимать пользовательское назначение и текущее состояние продукта.

## Уточнение неточных задач

Если задача пользователя сформулирована неточно, неоднозначно или допускает несколько существенно разных трактовок, не выбирай трактовку самостоятельно.

- Задай конкретные уточняющие вопросы, которые действительно влияют на результат.
- Не начинай изменение кода, пока критичные неоднозначности не устранены.
- Не задавай вопросы о деталях, которые можно однозначно определить из проекта, документации или существующей архитектуры.

## Laravel и структура проекта

Laravel следует стандартной структуре проекта, если задача явно не требует иного решения.

### JavaScript и Inertia/Vue

- JavaScript храни в `resources/js/`.
- Основная точка входа frontend-кода — `resources/js/app.js`.
- Инициализация Inertia/Vue находится в `resources/js/inertia-app.js`.
- Страницы Inertia храни в `resources/js/pages/`.
- Переиспользуемые Vue-компоненты храни в `resources/js/components/`.
- Общие frontend-сервисы и браузерные модули храни рядом с entrypoint, например `resources/js/pwa.js` и `resources/js/push.js`.
- Не добавляй inline JavaScript в Blade.
- Не дублируй frontend-логику между Vue-компонентами.
- Для внутренних переходов используй Inertia, а не обычную перезагрузку страницы, если маршрут поддерживает Inertia.

### Vite

- Для frontend используй Laravel Vite.
- Пока `package-lock.json` не отслеживается в репозитории, используй `npm install` в CI и не включай `cache: npm` в `actions/setup-node`, поскольку этот кэш требует lockfile. Если lockfile будет добавлен в репозиторий, правило можно пересмотреть.
- Точки входа объявляй в `vite.config.js`.
- Production-сборку выполняй командой `npm run build`.
- Не добавляй ручную минификацию или другой сборщик без отдельной необходимости.
- При изменении Vite-конфигурации сверяйся с актуальной официальной документацией Laravel Vite.

### CSS и мобильная адаптация

- Основные стили храни в `resources/css/`.
- Стили собирай через Vite.
- Любой новый или изменённый интерфейс сразу адаптируй под мобильные устройства.
- Мобильная адаптация является частью задачи, а не отдельным последующим этапом.

### Blade и Inertia shell

- Blade используется как минимальный серверный shell Inertia в `resources/views/app.blade.php`.
- Не возвращай отдельные Blade-страницы для инструментов, если соответствующая страница уже мигрирована на Inertia.
- Разметку страниц и переиспользуемые UI-элементы реализуй в Vue.
- Не помещай бизнес-логику в Blade.
- Не создавай параллельные Blade и Vue реализации одной страницы.

### Controllers

- Контроллеры находятся в `app/Http/Controllers/`.
- Для связанных инструментов используй понятную вложенную структуру каталогов.
- Контроллер принимает запрос, подготавливает данные и передаёт представлению.
- По мере роста бизнес-логики выноси её из контроллера в подходящие классы или сервисы.

### Routes

- Маршруты находятся в `routes/`.
- Используй именованные маршруты там, где на них есть программные ссылки.
- Бизнес-логику не помещай непосредственно в определения маршрутов, кроме простых случаев.

### Composer, Artisan и окружение

- Перед вызовом `php artisan`, которому нужны зависимости приложения, установи Composer-зависимости.
- Для установки зависимостей используй `composer install`.
- `vendor/` не коммить.
- Файлы окружения и секреты не коммить.
- Не храни production-секреты в исходниках или документации.

### Database и storage

- Изменения схемы базы данных выполняй через миграции.
- Локальную SQLite-базу не коммить, если задача явно не требует обратного.
- Каталоги, в которые Laravel должен писать на production, должны иметь корректные права доступа.
- Для AI/диагностики production SQLite используй `project:db-diagnostics` и только фиксированный read-only набор запросов. Не добавляй произвольный SQL через GitHub Actions и не выводи пароли, `.env`, VAPID private key, push endpoint/auth token или SSH credentials.
- **Не запускай database diagnostics без необходимости для текущей задачи.** Диагностика production БД выполняется только тогда, когда задача действительно требует проверки состояния БД, ролей, пользователей, push-подписок, миграций или других данных, которые нельзя определить из кода и конфигурации. Для frontend, UI, CSS, анимаций, игр и других задач, не связанных с состоянием БД, диагностику не запускать.

### Tests

- Существенную серверную логику сопровождай тестами.
- CI должен запускать тестовый набор перед production-деплоем.
- При изменении поведения обновляй соответствующие тесты.

## Production database diagnostics

- `.github/workflows/db-diagnostics.yml` предоставляет `workflow_dispatch` и безопасный `/db-diagnose` trigger через issue comment.
- Issue-comment trigger принимает команду только от владельца репозитория и выполняет на VPS только `php artisan project:db-diagnostics --json`.
- Диагностический вывод предназначен для проверки состояния production, ролей и push-инфраструктуры; он не является произвольным SQL-интерфейсом.
- Диагностику запускай только при наличии конкретной потребности текущей задачи; не используй её как общий health-check или по привычке.

## Проверка кода перед сборкой

После написания или изменения кода, но до запуска сборки, обязательно проведи собственное ревью изменённого кода на предмет синтаксических ошибок.

- Проверь синтаксис всех изменённых файлов соответствующими инструментами проекта.
- Отдельно проверь скобки, кавычки, точки с запятой, закрытие блоков и функций и другие конструкции, способные привести к ошибке сборки.
- Не запускай сборку до завершения этой проверки.

## README.md перед каждым коммитом

Перед каждым коммитом:

1. Открой `README.md`.
2. Сверь задачу с текущим описанием проекта.
3. Проверь, появилось ли новое пользовательское поведение, раздел или заметная возможность.
4. Если да — обнови `README.md` в том же коммите.

README должен быть коротким, понятным человеку без знания исходного кода и достаточно конкретным для AI, чтобы понять текущее состояние пользовательской части проекта.

В README не записывай пароли, токены, приватные адреса, внутренние секреты и другую чувствительную служебную информацию.

## Коммиты

### Одна логическая задача — один коммит

- **Один пользовательский таск = один коммит, даже если внутри таска меняются несколько файлов.** Если изменения нужны для одного и того же пользовательского результата (например, логика Vue + CSS-анимация одной игры/страницы), не дели их на отдельные коммиты по файлам.
- Разделяй коммиты только тогда, когда пользовательские задачи действительно независимы или изменения относятся к разным самостоятельным направлениям, которые можно завершить отдельно.

- Одну законченную логическую задачу оформляй одним коммитом.
- Если одна задача меняет несколько файлов одного направления, все эти изменения входят в один коммит.
- Не дроби одну задачу на несколько коммитов только из-за количества изменённых файлов.
- Сообщение коммита должно кратко описывать результат, а не процесс работы.

### Разные направления работы — разные коммиты

Перед созданием коммита определи направление каждого изменения.

К отдельным направлениям относятся, например:

- CI/CD и GitHub Actions;
- пользовательский интерфейс и frontend;
- backend и бизнес-логика;
- база данных и миграции;
- документация;
- инфраструктура и deployment;
- тесты.

Если потенциальный коммит затрагивает несколько разных направлений, раздели изменения на несколько коммитов.

Исключение: если одно направление технически невозможно отделить от другого без потери целостности изменения, допустимо объединить их, но сообщение коммита должно явно описывать связанную задачу.

Цель — чтобы каждый коммит представлял одну понятную и изолированную область изменения.

- Любой новый или изменённый интерфейс сразу адаптируй под мобильные устройства.

## Структура и архитектура

- Повторяющиеся элементы интерфейса выноси в компоненты.
- Логику, представление, стили и JavaScript размещай в соответствующих слоях.
- Не создавай параллельные способы решения одной и той же задачи без необходимости.
- Сохраняй существующую архитектуру, если задача не требует её изменения.

## Документация для человека и AI

Документация должна быть одновременно читаемой человеком и однозначной для AI, который продолжит проект.

Поэтому:

- используй реальные пути файлов и каталогов;
- фиксируй обязательные правила в повелительной форме;
- явно отделяй правила от описания текущего состояния;
- не полагайся на неявные договорённости из истории чата;
- при изменении правил сначала обновляй документацию;
- не добавляй в документацию то, что не соответствует фактическому состоянию репозитория.

## Безопасность

- Не записывай секреты и пароли в исходники.
- Не переноси GitHub Secrets в README, AGENTS.md и другие отслеживаемые файлы.
- Недоверенные данные GitHub Actions передавай в shell через переменные окружения, а не встраивай напрямую в исполняемый код.

## CI/CD и ошибки деплоя

Если пользователь сообщает, что в деплое есть ошибка:

1. Найди последний неуспешный workflow/deployment для актуального push в `main`.
2. Открой логи неуспешного job и определи конкретную причину ошибки, а не предполагай её.
3. Найди связанный с ошибкой код, конфигурацию или тест.
4. Исправь проблему в репозитории.
5. Перед сборкой проведи обязательную syntax review изменённых файлов.
6. Запусти необходимые проверки.
7. Запушь исправление в `main`.
8. Проверь новый workflow после push и, если он снова падает, продолжи разбор по его логам.
9. В итоговом отчёте укажи причину ошибки, внесённое исправление, commit и текущий статус CI/deploy.
10. Отдельно укажи статус документации.

При диагностике используй логи GitHub Actions, а не предположения.

## Отчёт о документации после push

После каждого push изменений в ветку в итоговом отчёте отдельной строкой указывай статус документации.

Если документация была обновлена, укажи это явно. Если для изменения документация не требовала обновления, также укажи это явно.

## Definition of Done

Задача считается законченной, когда:

- функциональность реализована;
- мобильная версия учтена;
- код находится в правильном слое;
- решение для Laravel сверено с актуальной официальной документацией, когда это применимо;
- README проверен и при необходимости обновлён;
- изменения одного направления не смешаны с несвязанными направлениями в одном коммите;
- правила документации соблюдены;
- каждый коммит содержит одну логическую и понятную область изменения;
- CI и связанные проверки не сломаны.

## Документация при каждом изменении проекта

**Обязательное правило проекта:** документация обновляется одновременно с изменением проекта, а не отдельным последующим этапом.

- После любого изменения проверяй, затрагивает ли оно README, AGENTS.md, архитектурное описание или другую проектную документацию.
- Если изменился подход, архитектура, deployment, CI/CD, дизайн-система, структура каталогов, публичное поведение, правила разработки или другой ключевой аспект — зафиксируй это в документации в том же логическом изменении.
- Не оставляй новые договорённости только в истории чата.
- README обновляй для пользовательского поведения и заметных возможностей.
- AGENTS.md обновляй для правил, обязательных подходов и инженерных ограничений.
- Документацию проверяй вместе с кодом перед завершением задачи.
