# Правила работы с проектом

## Отчёт после push

После каждого push изменений в ветку в итоговом отчёте необходимо отдельной строкой указывать статус документации:

**Документация обновлена:** да — документация проекта приведена в соответствие с внесёнными изменениями.

Если в конкретном изменении документация действительно не требовала изменений, это нужно явно указать вместо утверждения об обновлении.

Это правило относится к каждому push, который выполняется в рамках работы над проектом.

## Ошибки деплоя

Если пользователь сообщает, что в деплое есть ошибка, необходимо действовать по следующему правилу:

1. Найти последний неуспешный workflow/deployment для актуального push в `main`.
2. Открыть логи неуспешного job и определить конкретную причину ошибки, а не предполагать её.
3. Найти связанный с ошибкой код, конфигурацию или тест.
4. Исправить проблему в репозитории.
5. Запушить исправление в `main`.
6. Проверить новый workflow после push и, если он снова падает, продолжить разбор по его логам.
7. В итоговом отчёте кратко указать причину ошибки, внесённое исправление, commit и текущий статус CI/deploy.
8. Отдельно указать статус документации согласно правилу выше.

При диагностике использовать логи GitHub Actions: GitHub позволяет просматривать и искать логи каждого job и failed step workflow run.
